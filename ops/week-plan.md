## Facts for this week

The workers can't search the web. Use only the facts here, in ops/growth-brief.md and in the code. Never name a competitor site in copy.

Remux facts (checked 11-26-2026):
- MKV and MP4 are containers: boxes that hold the video, the audio and the subtitles. Remuxing moves those streams into the other container without decoding them, so the picture and sound don't change, and it takes about as long as copying the file. Converting (re-encoding) decodes and compresses again: it takes far longer and loses some quality.
- MP4 players (iPhone, iPad, Apple TV, many smart TVs, Premiere, iMovie, web pages) want H.264 or H.265 video and AAC, MP3, AC3 or E-AC3 audio. The iPhone Files app and the Apple TV app don't play MKV at all, even when the video inside is H.264. VLC for iPhone plays MKV directly.
- H.265 in MP4 must be tagged `hvc1` for Apple devices; files tagged `hev1` play sound with no picture there. This page writes `hvc1`.
- 10-bit H.264 (called Hi10P, common in anime releases) plays on computers but not on most phones and TVs in any container; it needs re-encoding.
- MP4 text subtitles are called mov_text (box name `tx3g`). iPhone, Apple TV, VLC, Plex and many TVs can turn them on. They are plain text: ASS styles, colors and positions are dropped; the words and times stay.
- Picture subtitles (PGS from Blu-ray, VobSub from DVD) can't go into an MP4 as they are. The route for PGS: save the track as .sup on /extract-subtitles-from-mkv/, read it into text on /sup-to-srt/, put the SRT back into the MKV on /add-subtitles-to-mkv/, then convert on /mkv-to-mp4/.
- Saving: Chrome and Edge on a computer write the new file straight to disk piece by piece (`showSaveFilePicker`); other browsers build one download from pieces of the original, which can fail for very large files.
- Chapters, attached fonts and tags in the MKV are not copied to the MP4.
- The desktop route, for guides only: `ffmpeg -i movie.mkv -map 0:v:0 -map 0:a -map 0:s? -c copy -c:s mov_text movie.mp4` (fails on picture subtitles; drop `-map 0:s?` then).

Cluster children: Timestamp `ts`; SimpleBlock and BlockGroup for kept video and audio tracks; skip everything else.
   - Block parsing, `parseBlock(b: Uint8Array, at: number)` where `b` = `Math.min(blockSize, 4096)` bytes read at the block's dataStart: `tn = readVint(b, 0, false)`; `rel` = signed int16 at `tn.length`; `flags = b[tn.length + 2]`; `lacing = (flags & 0x06) >> 1` (0 none, 1 Xiph, 2 fixed, 3 EBML); frames start at `p = tn.length + 3`. None: one frame `[dataStart + p, blockEnd)`. Laced: `count = b[p] + 1`, `p++`. Xiph: for each of the first count-1 frames add bytes until one is under 255 (255 means "add and go on"). EBML: first size = `readVint(b, p, false).value`; each next one of the first count-1 = previous + (`v.value - (2 ** (7 * v.length - 1) - 1)`); Fixed: every frame = (blockEnd - (dataStart + p)) / count, not an integer: throw 'This MKV is damaged.' Last frame = the rest. A lace header past `b.length`, or frames past blockEnd: throw 'This MKV is damaged.'
   - Keyframes: SimpleBlock `flags & 0x80`. BlockGroup: walk its children with 16-byte header reads; Block 0xa1 gives the block; keyframe unless a ReferenceBlock 0xfb child exists.
   - Per track keep plain arrays: `offset[]` (MP4 offset), `size[]`, `pts[]` in ms = `(ts + rel) * scale / 1e6` (laced frames share the block's pts), `key[]` (video). Also keep the source offset of each audio track's first frame (row 3 reads 8 bytes there).
   - No video frames: throw 'This MKV has no video data.'
6. Timing and boxes. `t0` = the smallest pts over kept video and audio frames. Movie timescale 1000.
   - Video, timescale 90000: `p[i] = Math.round((pts[i] - t0) * 90)`; `export function decodeOrder(p: number[]): { dts: number[]; ctts: number[]; shift: number }`: `dts` = p sorted ascending (a copy, numeric sort); `shift = max(0, max over i of dts[i] - p[i])`; `ctts[i] = p[i] - dts[i] + shift`. Durations: `dts[i+1] - dts[i]`; the last = DefaultDuration ns * 90 / 1e6 rounded if set, else the one before, else 3754.
